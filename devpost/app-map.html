TrayMath app map

A one-page guide to how TrayMath is put together, written from the finished code (commit noted at the bottom). It is a snapshot: if the code changes, the line numbers drift; the function names stay useful.

What the app is

One web page with two views. The planner is where a host describes the party and edits a tray order; the kitchen ticket is what the caterer opens from the link. Both ask the same counting engine, which shares each tray's pieces out between guest groups so no tray is counted twice. The order is stored in the page address, nowhere else.

One action, end to end: “Plan my trays”

Reference route (not toured live with the learner): follow it in an editor with the app open.

1 · The click — src/planner.js, search case 'plan':

One click listener on the whole planner reads data-act from the button. For plan it checks the party is valid with buildGroups(state), replaces state.order with autoPlan(MENU, state), and calls render().

2 · The counting — src/engine.js, coverage() and autoPlan()

coverage() builds a small network: source → each tray (capacity = its pieces) → every group that can eat it → sink (capacity = what the group needs). It connects groups to the sink one at a time, most constrained first, and pushes flow after each, so restricted guests keep their pieces. The result per group is need, onTable (naive count), covered (actually theirs) and short. autoPlan() just tries “one more of each tray” and keeps the best, using coverage() as the judge.

3 · The result on screen — src/planner.js, function renderBoard

Draws one row per group: the three numbers, one plate per guest (plates() in src/view-helpers.js), the short line and up to two fixes from suggestFixes(). The same render() then writes the plan into the address through encode() in src/order-link.js.

To change this, start here

  • Menu, prices, labels: MENU in src/menu.js. Each tray lists the diets it suits and the allergens it contains.
  • How much each guest eats: PARTY_TYPES (piecesPerGuest) and SWEET_SHARE in src/menu.js.
  • Who can eat what: compatible() in src/engine.js.
  • Colours and type: tokens at the top of src/styles.css; direction in DESIGN.md.
  • The caterer's ticket and labels: mountTicket() in src/ticket.js; label print styles at the bottom of src/styles.css.

A practice to reuse

Turn each acceptance criterion into a named check. The PRD line “the same tray is never counted twice” became the test the same tray is never counted twice (enough on paper, short in reality) in tests/engine.test.js, and a browser step in tests/journey.mjs. When the first demo idea (“remove the fruit skewers and the vegans go short”) turned out not to happen, running the engine on the sample party showed it before any screen existed, and the plan was revised on paper (devpost/checklist.md > Revisions) before the demo was recorded. On any project: write the criterion so it can be checked by looking, then make the check run with one command.

Run it again

python3 -m http.server 47811 in the project folder, open http://localhost:47811/. Tests: npm test; browser journey: node tests/journey.mjs http://localhost:47811/.
